4. ENDPOINTS
================================================================================
Both follow the existing API conventions exactly:
  require_once auth.php -> 401 JSON if $_SESSION['user_id'] is empty ->
  session_write_close() -> Content-Type: application/json; charset=utf-8 ->
  $config = require config.php -> PDO ERRMODE_EXCEPTION + FETCH_ASSOC ->
  try/catch(Throwable) that error_log()s the real message server-side and
  returns a generic {"success":false,"error":"Internal server error"}.
Both are SELECT-only. Neither writes anything, anywhere.

--- api_energy.php ---------------------------------------------------------
GET params:
  ?category=CT|CCP|CHWP   unknown value falls back to CT (never errors)
  ?from=YYYY-MM-DD        optional
  ?to=YYYY-MM-DD          optional

Returns:
  success, category, categories[], available{min,max}, from, to,
  units[{unit}], days[{date, values{"<unit>":{total,usage}},
                       sum_total, sum_usage}]

Notes:
  - Unit columns are DISCOVERED from information_schema.columns, not
    hardcoded. Verified live: CT = 1,2,3,4,5,6,9,10,11,12,13 (no 7 or 8);
    CCP = 1..9; CHWP = 1..9. A hardcoded list would be wrong for at least
    one category.
  - Each discovered name is re-validated against /^[a-z]+_(\d+)$/ and
    prefixed with the category's own prefix before it is used in SQL text.
    Table names come from the PHP map only — no request data reaches a
    table or column position.
  - Dates validated with a strict regex + checkdate(), so 2026-02-30 and
    2026-13-45 are rejected rather than passed through.
  - A reversed range is swapped, not rejected.
  - Empty table -> a valid empty response (success:true, days:[]), not 500.
  - Default window: last 31 days ending at the newest snapshot.
  - `usage` NULL is preserved as null (see Section 6).

--- api_temp_rh_hourly.php -------------------------------------------------
GET params:
  ?metric=temp|rh        unknown value falls back to temp
  ?from=YYYY-MM-DD       optional
  ?to=YYYY-MM-DD         optional

Returns:
  success, metric, metrics[], unit, available{min,max}, from, to,
  rooms[{key,room_type,room_name,label}], hours[{recorded_at, values{},
  read_at_min, read_at_max}]

Notes:
  - temp_rh_hourly is LONG format; the pivot to one column per room is done
    in PHP, not as dynamic SQL, so no column name is ever built from data.
  - The room list query is deliberately NOT filtered by metric, so the
    column set is identical for temp and rh over the same dates. Switching
    the metric must not move the columns.
  - room `label` uses the same rule as api_room.php ("<room_type> <room_name>"),
    so a room reads identically in the live room cards and in the hourly
    table. (Originally "on the live tab and the history tab" — the hourly
    table is now a view inside the same ROOM TEMP & RH tab; see Section 12.)
  - Date bounds are widened to whole days (" 00:00:00" / " 23:59:59") so a
    snapshot at 23:00 is not cut off at midnight.
  - read_at is tracked as a min/max pair per hour rather than assumed
    identical across points.
  - Default window: last 7 days ending at the newest snapshot.

5. FRONTEND (index.php + style.css)
================================================================================
Navigation
  Two new buttons were added to the existing nav: ENERGY, TEMP & RH HOURLY.
  [SUPERSEDED — the TEMP & RH HOURLY button was later removed; see Section 12.
   ENERGY is still its own nav tab.]

Filter bar
  A new #pageFilters container sits BETWEEN the section header and
  #equipmentGrid, so a re-render cannot destroy inputs the user is typing
  into. Built by buildFilterBar(): a selector (CATEGORY / METRIC) plus FROM
  and TO date inputs and APPLY / RESET buttons. RESET clears the dates but
  keeps the selected category/metric. renderEquipment() clears the bar up
  front for every page, so it appears only where a view builds one: the
  ENERGY tab, and ROOM TEMP & RH in its Hourly History mode.
  [SUPERSEDED — the original wording said "Every other tab calls
   clearPageFilters(), so the bar exists only on the two history tabs."
   That was also wrong at the time: the clear sat at the END of
   renderEquipment(), and several branches return early, so the bar leaked
   across EF / ALARM / ENERGY. See Section 12.]

Tables
  Div-based, matching the rest of the app — the app has no <table> markup
  anywhere. createTable() sets --history-cols for the CSS grid, and the
  first column is sticky-left with a sticky-top header. The whole table
  scrolls horizontally inside .history-table-wrap.

Display rules
  - ENERGY shows TWO numbers per unit: TOTAL n (cumulative meter reading)
    and UNIT n (that day's consumption), so a meter reset is visible as a
    jump in TOTAL instead of being silently absorbed.
  - A NULL usage renders as a dimmed "--", visually distinct from a real 0.
  - TEMP & RH HOURLY has a metric selector rather than showing temp and rh
    side by side: that would be ~20 room columns and unreadable.
  - Each hourly row carries a READING AT column. When the sample times
    within an hour differ it shows "min – max" rather than hiding the
    spread. (Live data currently has min == max, so it shows a single time;
    the range path is covered by the test suite.)

Refresh behaviour
  Neither history page auto-refreshes. Past data does not change, so a 10s
  poll would re-fetch identical rows forever. Neither polls api_alarm.php
  either — isHistoryPage() guards safeLoadAlarmData(). Returning to a live
  tab re-baselines knownAlarmIds silently, so an alarm that arrived while
  history was on screen is recorded without firing on navigate-back.

Security
  Every DB-derived string is written with textContent, never innerHTML.
  Filter values are encodeURIComponent()'d into the query string.
