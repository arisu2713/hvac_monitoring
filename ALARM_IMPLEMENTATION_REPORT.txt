5. API DESIGN  (api_alarm.php)
--------------------------------------------------------------------------------

Conventions matched to the existing api_*.php endpoints:

  * require_once __DIR__ . '/auth.php'
  * 401 + {"success":false,"error":"Authentication required"} when
    $_SESSION['user_id'] is empty
  * session_write_close() before DB work
  * Content-Type: application/json; charset=utf-8
  * $config = require __DIR__ . '/config.php' (existing DB config, reused)
  * PDO with ERRMODE_EXCEPTION + FETCH_ASSOC
  * try/catch(Throwable) -> error_log() server-side, generic
    {"success":false,"error":"Internal server error"} to the client

READ-ONLY: one SELECT for counts, one prepared SELECT for rows. No INSERT,
UPDATE, DELETE, or DDL anywhere in the file.

Response shape:

  {
    "success": true,
    "counts": { "active_alarm": N, "active_warning": N, "active_total": N },
    "window_hours": 24,
    "server_time": "YYYY-MM-DD HH:MM:SS.ffffff",
    "alarms": [ { "id", "event_class", "source", "equip_type", "equipment",
                  "point_id", "ef_point_id", "panel_no", "ip_address",
                  "metric", "description", "status", "value",
                  "limit_min", "limit_max", "raised_at", "cleared_at" } ]
  }

Design decisions:

  * Counts are computed over the whole table (WHERE status='ACTIVE'), NOT over
    the returned rows, so the summary stays correct when history is truncated.
  * Cleared rows are windowed because history grows without bound. ?hours=
    default 24, clamped to 1..168. ACTIVE rows are always returned regardless
    of age.
  * ?limit= default 500, clamped 1..1000. Both parameters are cast to int and
    clamped, never interpolated raw. The row LIMIT is bound with
    PDO::PARAM_INT; the interval is a validated integer, not user text.
  * Ordering: (status='ACTIVE') DESC, raised_at DESC — active rows lead.
  * active_key is deliberately NOT returned. It is the pollers' internal
    de-duplication key (UNIQUE index); the page's stable identifier is id.
  * server_time comes from NOW(6), the same database clock the pollers stamp
    raised_at with, so the window and the reported time share one clock.
  * Numeric fields are cast ((int)/(float)) so the JSON types are stable.

--------------------------------------------------------------------------------
6. ALARM STATE HANDLING
--------------------------------------------------------------------------------

ACTIVE and CLEARED are rendered as two separate groups. ACTIVE is first, with
a red/amber left accent and a red-tinted row background; CLEARED sits below in
a receded grey group, labelled with the window ("CLEARED (last 24h)").

Cleared rows show their cleared_at timestamp; active rows show "--" in that
column, since a null there means "still active", not "unknown".

A cleared row in alarm_events is immutable history: the poller clears in place
(status='CLEARED', cleared_at set, active_key=NULL) and a recurrence INSERTs a
new row, so a CLEARED event never reactivates.

Per §4, this is kept distinct from the pre-existing per-card alarm colouring.
The per-card red/amber blinking comes from each api_*.php returning an
instantaneous `alarm` flag and *_min/*_max bounds — a live snapshot with no
identity or history. The global page reads the event log. The two can
disagree, and PROJECT.md section 12 says so explicitly.

--------------------------------------------------------------------------------
7. ALARM vs WARNING HANDLING
--------------------------------------------------------------------------------

event_class is an enum with exactly two values and they are kept conceptually
separate at every layer:

  ALARM   = native equipment alarm/status (poller's TryBuildNativeAlarm)
  WARNING = threshold / value-limit violation (poller's TryBuildWarning)

Separated in: the summary counters (Active Alarm / Active Warning), the row
badge (red ALARM / amber WARNING), and the active row's left accent colour.
No third category exists and none was introduced.

--------------------------------------------------------------------------------
8. SOUND BEHAVIOR
--------------------------------------------------------------------------------

Web Audio API generated tone. No external CDN, no third-party audio service,
no audio asset of any kind — two 880 Hz square-wave beeps built from an
OscillatorNode + GainNode.

Short exponential gain ramps (0.0001 -> 0.18 -> 0.0001) are used instead of
hard starts/stops, because a raw square wave produces an audible click.

The AudioContext is created lazily on first need and reused. It is never
created at page load, so a silent page allocates nothing.

  Initial page load : silent. The first API response only records the baseline
                      of active ids (see section 9).
  New alarm         : sounds once, on the poll that first sees the new id.
  Existing alarm    : never retriggers; the id is already in the known set.
  Same event        : cannot repeat, because detection is by id, not by
                      position or array order.

--------------------------------------------------------------------------------
9. NEW ALARM DETECTION
--------------------------------------------------------------------------------

State: `knownAlarmIds` — a Set of String(alarm.id) for rows with
status === 'ACTIVE'. alarm_events.id is the bigint unsigned primary key, which
is stable across polls and independent of row order and of array position.

  1. First response  : knownAlarmIds === null, so the current active id set is
                       recorded and NO sound is played. Alarms already active
                       when the page opens never sound.
  2. Later responses : the current id set is diffed against knownAlarmIds. Any
                       newly appearing ACTIVE id triggers exactly one sound,
                       then knownAlarmIds is replaced with the current set.
  3. Known alarms    : already in the set, so they never sound again.
  4. Cleared alarms  : filtered out of the id set entirely (status !== 'ACTIVE')
                       and never sound. They still update the display normally.
  5. Muted           : ids are still tracked while muted, so unmuting does not
                       replay alarms that arrived during the mute.

Ordering is deliberately NOT used as a signal. Reordering the rows, or
truncating the list at the limit, cannot fabricate or lose a new alarm.

--------------------------------------------------------------------------------
10. MUTE BEHAVIOR
--------------------------------------------------------------------------------

A single MUTE / UNMUTE button in the alarm toolbar (label and aria-pressed
reflect the current state).

Mute:
  * silences alarm sound              (soundAlarm() returns early)
  * does NOT hide alarms              (the list is rendered identically)
  * does NOT clear alarms             (no status is touched)
  * does NOT modify alarm_events      (the API is read-only; mute never
                                       reaches the server)
  * does NOT modify any database state

Mute affects the audible alert only. A muted page still shows every active
alarm, still updates counts, and still tracks newly arriving ids.

--------------------------------------------------------------------------------
11. localStorage BEHAVIOR
--------------------------------------------------------------------------------

Key:   hvac_alarm_muted
Value: "1" (muted) or "0" (unmuted)

Written by toggleAlarmMute() on every toggle. Read by readAlarmMuted() into
`alarmMuted` at page init, BEFORE the first poll, so a refresh during an active
alarm never produces a burst of sound.

Both the read and the write are wrapped in try/catch. In private mode or with
site data blocked, localStorage can throw or come back empty; the page then
degrades to "unmuted for this session" rather than failing to render. This key
is the only thing the alarm feature stores, and it never leaves the browser.

14. LIMITATIONS / FOLLOW-UP ITEMS
--------------------------------------------------------------------------------

  1. alarm_events is currently EMPTY (0 rows), so the page has been validated
     against synthetic payloads and the real empty state, not against live
     production alarms. The end-to-end path — poller writes a row, the browser
     sounds — has not been observed with real data. This is the single most
     important thing to confirm once the Phase 2B pollers are deployed.

  2. The pollers that WRITE alarm_events (BACnet Phase 2B and EF Phase 2B) are
     not deployed. Until they are, this page will correctly show zero alarms.

  3. Cleared history is windowed at 24h and capped at 500 rows. Both are
     server-side clamps, adjustable via ?hours= and ?limit=. There is no
     pagination or date-range filter in the UI yet.

  4. The sound is a fixed two-beep tone. It does not differentiate ALARM from
     WARNING, and it does not repeat while an alarm stays unacknowledged —
     a new alarm beeps once and then goes quiet. If a persistent/repeating
     alert is wanted for standing alarms, that is a deliberate follow-up.

  5. Sound is only as reliable as the browser's autoplay policy. A wall
     display that is never touched may have a suspended AudioContext, in
     which case the notice asks the user to press MUTE then UNMUTE once.
     Unlocking audio at login would be a cleaner fix.

  6. Mute state is per-browser, per-origin (localStorage). It is not shared
     between the wall display and an operator's laptop, and it does not
     survive clearing site data. A server-side acknowledgement model would be
     a larger, separate piece of work.

  7. There is no acknowledgement/shelve concept. Muting is global to the
     browser and silences everything, including a WARNING the operator might
     still want to hear.

  8. ALARM_IMPLEMENTATION_REPORT.txt and the other *.md / *.sql files in the
     repo remain untracked. Nothing was staged or committed (§17).
