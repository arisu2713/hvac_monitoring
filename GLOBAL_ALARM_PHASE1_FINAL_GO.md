## Alarm categories

There are exactly two event categories:

### ALARM

Generated by a native equipment alarm/status point.

Examples:
- AHU native BI alarm
- HVAC_SC native BI alarm
- EF native alarm/status event
- communication alarm where applicable

### WARNING

Generated by a threshold/value-limit violation.

Examples:
- AHU temperature above threshold
- ROOM temperature/RH above threshold
- HVAC_SC value exceeding configured threshold

IMPORTANT:

WARNING and ALARM are conceptually different.

Do NOT convert a threshold violation into a native ALARM.
Do NOT convert a native ALARM into a WARNING.

Both are stored in the same `alarm_events` table.

An equipment may legitimately have both an ALARM and a WARNING active simultaneously. They must remain separate events.

## Proposed definitions

### id

    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT

Primary key.

Reason:
- append-heavy event log
- one row per alarm occurrence
- alarm may recur many times
- avoids dependence on a natural key

### event_class

    ENUM('ALARM','WARNING') NOT NULL

This is the primary distinction between native alarm and threshold warning.

### source

    VARCHAR(32) NOT NULL

Identifies the originating writer/poller.

Expected future examples:

    AHU_POLLER
    HVAC_SC_POLLER
    EF_POLLER
    ROOM_POLLER

Do not hard-code these as ENUM values in Phase 1.

### equip_type

    VARCHAR(50) NULL

Equipment/source classification.

Use actual project values.

Important:
- CT currently has an existing trailing-space issue in source data.
- Do not silently alter existing source data.
- Future poller contract should normalize this when writing.

### equipment

    VARCHAR(64) NOT NULL

Human-readable equipment identity.

Examples:

    AHU 65
    CCP 3
    EF 27

### point_id

    VARCHAR(32) NULL

For normal project points such as AHU/HVAC_SC/ROOM.

### ef_point_id

    INT UNSIGNED NULL

For EF point identity.

### panel_no

    INT NULL

Reserved for sources where panel identity is authoritative, especially EF communication/event context.

Do not decide EF alarm granularity in Phase 1.

### ip_address

    VARCHAR(45) NULL

For communication-source identity where IP is relevant.

### metric

    VARCHAR(32) NULL

Optional point/measurement detail.

Examples may include:

    TEMP
    RH
    CURRENT
    STATUS

Do not invent additional metric taxonomy in Phase 1.

### description

    VARCHAR(255) NOT NULL

Human-readable alarm description.

This is intended for the global alarm page.

### status

    ENUM('ACTIVE','CLEARED') NOT NULL DEFAULT 'ACTIVE'

Current lifecycle state of the event.

### active_key

    VARCHAR(200) NULL

Deterministic identity for an ACTIVE alarm condition.

This is the duplicate-prevention mechanism.

### value

    FLOAT NULL

Actual value captured when the alarm was raised.

For native status alarms this may be NULL where not applicable.

### limit_min

    FLOAT NULL

Lower threshold, when applicable.

### limit_max

    FLOAT NULL

Upper threshold, when applicable.

For a simple high-limit warning, only limit_max may be populated.

### raised_at

    DATETIME(6) NOT NULL

Timestamp supplied explicitly by the poller.

Do NOT use DEFAULT CURRENT_TIMESTAMP.

Reason:
- project uses naive WIB timestamps
- local DB SYSTEM timezone is WIB
- hosting DB SYSTEM timezone is UTC
- database-generated NOW()/CURRENT_TIMESTAMP could therefore produce inconsistent timestamps

### cleared_at

    DATETIME(6) NULL

Explicit recovery timestamp supplied by the poller.

Do NOT use DEFAULT CURRENT_TIMESTAMP.

## Duplicate prevention

Use:

    UNIQUE KEY uq_alarm_active (active_key)

MariaDB allows multiple NULL values in a UNIQUE index.

Therefore:

ACTIVE:
    active_key = deterministic identity

CLEARED:
    active_key = NULL

This allows:
- only one active event for a given condition
- unlimited historical cleared events
- recurrence to create a new event after the previous event is cleared

---

## Active-key concept

The exact poller contract will be defined later.

The schema must support deterministic identities such as:

Native alarm:

    NATIVE_ALARM:<point_id>:<metric>

Threshold warning:

    THRESHOLD_AI:<point_id>:<metric>:<max|min>

EF point:

    EF_POINT:<ef_point_id>:<metric>

EF communication:

    EF_COMM:<panel_no>

These are examples of the identity strategy only.

Do not implement poller logic in this phase.

## Lifecycle

Alarm appears:

    INSERT
    status = ACTIVE
    active_key = identity

Alarm remains active:

    NO INSERT
    NO UPDATE required merely because another poll occurred

Alarm clears:

    UPDATE existing row
    status = CLEARED
    cleared_at = recovery timestamp
    active_key = NULL

Alarm appears again later:

    INSERT new row

Do not create one row every 30 seconds while an alarm remains active.

---

## Integrity constraint

Include:

    CHECK (
        (status = 'ACTIVE' AND active_key IS NOT NULL)
        OR
        (status = 'CLEARED' AND active_key IS NULL)
    )

Purpose:
prevent an inconsistent state between status and active_key.

## Test strategy

1. Insert WARNING ACTIVE.
2. Attempt duplicate ACTIVE identity.
3. Confirm duplicate is rejected/prevented.
4. Clear the event.

6. Insert same alarm again.
7. Confirm a new event row can exist.
